# 超上限提示：横幅改胶囊 —— 复核说明（供外部模型审阅）

> 目的：把当前实现、硬约束、已排除方案和候选改法原样列出，请独立复核「能不能在不改颜色、不改高度的前提下把横幅改成胶囊形状」，并指出方案里的坑。
> 本轮只做分析，**没有改任何代码**。仓库状态：`D:\mixcalc-harmony`，HEAD = `7d1615e`，工作区干净，版本 `0.3.7 / 1000307`，HarmonyOS SDK 6.0.1(21)。

## 1. 需求（三条硬约束，缺一不可）

1. **形状要变成胶囊**（两端全圆角，像系统 toast 那种），不再是现在横贯整个表格、四角方正的色条。
2. **背景色 `#FBE3E3` 与文字色 `#7A1F1F` 都不许变**（底边线 `#E8B4B4` 是否保留见 §5 待定）。
3. **高度不许变**：现在高度是表头行高 40vp（`HEAD_H`），胶囊本体仍必须 40vp。

## 2. 当前实现（`entry/src/main/ets/table/MixCalcTable.ets:2708-2726`）

位于表格根 `Stack()` 内，与表头、表体、单元格编辑器平级：

```ets
// 超上限横幅：正好压在表头这一行（y=0、高=表头高），
// 不用系统 toast 的 offset——状态栏/标题栏高度因机型而异，toast 会压到交界处。
// hitTestBehavior 设成 None，不挡底下的表头点击。
if (this.limitBannerOn) {
  Text(t(this.lang, 'shed.overLimit').replace('%d', MAX_SHED_NUMBER.toString()))
    .width('100%')
    .height(this.hh())            // hh() = HEAD_H = 40（MixCalcTable.ets:23 / 653）
    .position({ x: 0, y: 0 })
    .fontSize('15vp')
    .fontWeight(FontWeight.Bold)
    .fontColor('#7A1F1F')
    .textAlign(TextAlign.Center)
    .maxLines(1)
    .backgroundColor('#FBE3E3')
    .borderWidth({ bottom: 1 })
    .borderColor('#E8B4B4')
    .hitTestBehavior(HitTestMode.None)
    .zIndex(8)
}
```

配套状态与生命周期（不打算改）：

## 3. 约束的来由（不要提议改回系统 toast）

11-14 之前这里用的是 `promptAction.showToast({ alignment: Alignment.Top, offset: { dx: 0, dy: 72 } })`，问题是 **72 是硬编码**：状态栏 + 标题栏的总高度因机型/平板而异，机型一变 toast 就压到两栏交界处，观感很差。所以改成页面内组件，用 `position({x:0,y:0}) + height(表头高)` 精确贴在表头这一行。

查本机 SDK `ets/api/@ohos.promptAction.d.ts` 的 `ShowToastOptions`，全部字段只有：
`message / duration / bottom / showMode / alignment / offset / backgroundColor / textColor / backgroundBlurStyle / shadow / enableHoverMode / hoverModeArea`。

**没有 `height`、`borderRadius`、`fontSize`、`padding`、`width`** —— 也就是说回到 `showToast` 虽然能保住颜色，但高度必然是系统主题值（约 32vp 左右），且位置又退回 `alignment + offset` 的老问题。**故方案只能留在页面内。**
（另有 API 18 的 `openToast()` 返回 id + `closeToast(id)` 可以主动收起，但起一个系统级浮层窗口依旧控制不了高度，且 `position / zIndex / HitTestMode.None` 全部失效。）

## 4. 候选方案 A（我目前倾向的最小改动）

外层几何一行不动，只把「全宽实心 Text」拆成「全宽透明 Row + 居中的自适应宽胶囊 Text」：

```ets
if (this.limitBannerOn) {
  Row() {
    Text(t(this.lang, 'shed.overLimit').replace('%d', MAX_SHED_NUMBER.toString()))
      .height(this.hh())                        // 40vp 不变
      .borderRadius(this.hh() / 2)              // 20vp = 高度一半 → 胶囊
      .padding({ left: 16, right: 16 })
      .fontSize('15vp')
      .fontWeight(FontWeight.Bold)
      .fontColor('#7A1F1F')
      .textAlign(TextAlign.Center)
      .maxLines(1)
      .backgroundColor('#FBE3E3')
      .constraintSize({ maxWidth: '92%' })      // 长文案兜底
      .textOverflow({ overflow: TextOverflow.Ellipsis })
  }
  .width('100%')
  .height(this.hh())
  .justifyContent(FlexAlign.Center)             // 水平居中，不用 measureText 量宽
  .alignItems(VerticalAlign.Center)
  .position({ x: 0, y: 0 })
  .hitTestBehavior(HitTestMode.None)            // 穿透，不挡表头点击
  .zIndex(8)
}
```

- 高度：外层仍 40vp、仍贴 y=0 → 位置与占位不变；
- 颜色：两个色值原样搬到内层 Text；
- 形状：内层去掉 `width('100%')`，宽度随内容 + 左右 16vp padding → 两端 20vp 圆角 → 胶囊。

替代做法是直接把 `borderRadius(this.hh()/2)` 加在现在的全宽 Text 上 —— 但那只是「全宽圆角矩形」，两端仍是直边，不是胶囊，不满足约束 1。

## 5. 需要复核的具体问题

1. **垂直居中**：Text 固定 `height(40)` + 左右 padding 时，文字是否严格垂直居中？是否还需要显式 `.align(Alignment.Center)`？
2. **百分比约束**：`constraintSize({ maxWidth: '92%' })` 在「被 `position` 定位的 Row」的子节点上，百分比是否按 Row 宽度解析（而不是按屏幕宽）？
3. **单边边框 + 圆角**：现在 `.borderWidth({ bottom: 1 }) + .borderColor('#E8B4B4')`。套上 20vp 圆角后，ArkUI 会画出「圆角轮廓 + 一条贯穿的直底边」还是自动沿圆角收边？如果割裂，是删掉底边线、还是改整圈 `.border({ width: 1, color: '#E8B4B4', radius: 20 })`？（后者形状变、颜色不变）
4. **点击穿透**：`HitTestMode.None` 放在 Row 上，是否连子节点一起不响应触摸，确保底下的表头照常可点？
5. **文案长度**：`shed.overLimit` 中文是「棚号超过上限，最多 1-99」这类短句，英文是 `Input exceeds the limit: max shed number is 99`。手机宽 360vp 下胶囊最宽可用约 331vp（92%），减去左右 32vp padding 剩约 300vp，15vp 加粗放得下吗？是否需要按 `lang` 分别给不同 `maxWidth` 或允许两行？
6. **是否有更合适的官方组件**：ArkUI 里是否有现成的「Chip / Tag / Toast 样式容器」能直接给出胶囊外观，避免自己拼 Row + Text？
7. **视觉副作用**：胶囊居中后，表头左右两侧会重新露出来（现在是整条全宽色块盖住）。粉底压在白/浅色表头上对比度是否可接受？是否需要在胶囊外层补一层极淡的半透明底来保住原有「盖住表头」的观感？（注意：这会把「背景色不变」变成「多一层底色」，需明确裁决。）
8. **还有没有更简单的写法**：例如单独用 `Stack` + `margin` 居中、或者 `Blank()` 撑开等，有没有比 Row 更稳的等价写法。

## 6. 验收标准（改完怎么算对）

## 8. 外部方案评估：`openCustomDialog` 那条路能不能走

外部（华为小艺 / DeepSeek）给出的结论是：原生 showToast 与 openToast 都没有 height / cornerRadius / fontSize，**唯一稳妥路径是用 `UIContext.getPromptAction().openCustomDialog` 自己画一个"长得像 toast"的提示框**。

**事实部分成立**：我独立核过本机 SDK `@ohos.promptAction.d.ts`，`ShowToastOptions` 确实只有 `message / duration / bottom / showMode / alignment / offset / backgroundColor / textColor / backgroundBlurStyle / shadow / enableHoverMode / hoverModeArea`，没有任何尺寸与圆角字段；`openCustomDialog` 的 `BaseDialogOptions` 确实有 `width / height / cornerRadius / borderWidth / borderColor / shadow / backgroundBlurStyle / maskColor / isModal / autoCancel / keyboardAvoidMode / focusable(since 19)`。所以"自定义弹窗能完全控制样式"这句话本身没错。

**但它推荐的路径对我们的场景不成立**，三条硬理由：

1. **位置又变回"猜一个常数"**。横幅必须正好压在表头这一行，而表格上方还有标题栏（`Index.ets:700` `title_bar_bg`）和状态栏。弹窗的 `alignment + offset` 是相对**窗口/屏幕**的，要落到表头就得填一个"标题栏高度"的固定值 —— 跟 11-14 废掉的 `offset: {dy: 72}` 是同一个错误，只是数字换个大小。机型、平板、折叠屏一变就错位。
2. **横幅是在用户打字时弹的，弹窗会抢焦点**。`warnOverLimit()` 由 `applyEdit()`（`MixCalcTable.ets:1099`）触发，此刻 `TextInput` 正在编辑、键盘正弹起。`openCustomDialog` 默认 `isModal: true`、可获取焦点，弹出来打断焦点就会触发我们的 `onBlur` 结算链路，把正在编辑的单元格结算掉、键盘收起 —— 比原来那个 toast 更糟（toast 不抢焦点）。靠 `isModal: false` + `focusable: false`（API 19 起才有）能缓解，但那是依赖版本行为的细节，脆弱。
3. **生命周期从 1 个布尔变成 controller + id**。现在 `@State limitBannerOn` + `setTimeout(2200)`，换格 `hideLimitBanner()` 一置 false 就收。换成 `openCustomDialog(): Promise<number>` 要拿 id、`closeCustomDialog(id)`、处理快速连续触发时 open 未 resolve 就要 close 的竞态，页面销毁还要兜底关闭。

另外它自己也提醒了"自定义弹窗不享受 toast 的软键盘自动避让" —— 而我们的场景键盘常开，这条对弹窗是负担；对页面内组件则不存在（横幅固定在表头，表格自己滚动）。

**结论**：做法可行、但选错了工具。页面内 `Row + Text` 胶囊（§4 方案 A）本来就是"零新窗口、零 offset 猜测、不碰焦点"，外部方案唯一能补的"高度/圆角/字号可调"在页面内组件里本来就是自由属性。只有当需求变成"要悬浮在屏幕中央、带阴影模糊的系统 toast 观感"时，才该走 `openCustomDialog`，代价是上面三条。
