## 2. 本轮用户点名的三条改动（安卓最该先同步）

这三条是真机实测出来的同一条链：按「下一行」/ 键盘「下一步」时，**该删的死行没删、光标没跟着上移**。鸿蒙已改完并出包验证，安卓要照着改。

### 2.1 换格必须走「完整结算」（含整行回收）

| | 鸿蒙（改动前 → 改动后） | 安卓（当前） |
|---|---|---|
| 手点其它单元格 | `openEditor()` → `settleRowsAndPad([])` → `settleRows()` → `recycleDeadRows()`，**会删行** | `handleTap()` → `editor.end()` → `onCellEditEnd()` → `post(settleZeroRows(emptied))`，**会删行** |
| 「下一步 / 下一行」 | ❌ 原来只调 `settleZeroRows()` → `settleZeroRowData()`，**只清料/水/平均，不删行** → 已改为 `settleRowsAndPad([])` | `moveFocusToNextEditableCell()` / `moveFocusToNextRow()` 本身**不调结算**，靠 `CellEditorOverlay.begin()` 换格时 `notifyEditEnd()` 间接触发 |

- 鸿蒙最终改动（`entry/src/main/ets/table/MixCalcTable.ets`）：`nextRowDown():1356`、`nextCell():1410` 两处，把 `this.settleZeroRows()` 换成 `this.settleRowsAndPad([])`；`settleZeroRows()` 保留，仅供 `aboutToAppear` 载入时清历史脏数据。
- **关键**：只有真正换格才结算；上面任何提前 `return` 的分支，编辑还留在原格，绝不能清数据。
- 死行定义：有效棚数为 0（按声明文本重算、后行优先），但「填过棚号或填过数据」的行 → 整行移除、下面的行上顶、底部补空行保持行数守恒；**纯空行绝不删**（是留给用户录入的容量）。完整算法见 5.4。

> 安卓注意：安卓 `MixCalcActivity.settleZeroRows()`（`:677-705`）**本身已经包含 `recycleDeadRows` + 兜底清 + `finishRowRemoval`**，不是鸿蒙那个「只清数据」的 `settleZeroRows`。两端同名函数含义不同，别按名字照搬。安卓真正要补的是「换格路径能不能走到结算」，见 2.2。

### 2.2 「下一行」要跳到下一行**可用的单元格**，别死守同一列

- 鸿蒙症状：在料量列按「下一行」，下一行是空行（`shedCount=0` → 料量/平均格 `isCellEnabled=false`），旧逻辑按「回车到头」直接 `return`，**既不换格也不结算**，死行就一直留在屏上。
- 鸿蒙最终规则（`nextRowDown()`，`MixCalcTable.ets:1308-1362`）：
  1. 目标行固定 `editingRow + 1`；
  2. **同列能编辑就保持同列**；
  3. 同列不能编辑 → 按 `editableColumns()` 顺序扫这一行，跳到**第一个 `isCellEnabled` 为真的列**（空行通常就是棚号列）；
  4. 整行一个可编辑格都没有，才 `return`（回车到头）；
  5. 换格一发生就照常 `settleRowsAndPad([])`，死行回收自然跟着跑。
- 未动：120ms 节流、顺序提示、`applyEdit` 提交、`moveEditor()`、`nextCell()` 的扫描规则。
- 键盘「下一步」`nextCell()`（`:1364-1419`）本来就向后循环扫可编辑格并跳过不可编辑格，本轮只补了 2.1 的结算与 2.3 的重定位。

> 安卓现状（核对过）：`moveFocusToNextEditableCell()`（`:831-881`）跨行时**已经会扫下一行所有可编辑列**，这条符合新规则；但 `moveFocusToNextRow()`（`:884-905`）在 `:897-900` 写着
> `if (data == null || !isCellEnabled(columnId, data, nextRow)) return;` —— **死守同列、空行直接返回**，浮层不 `end()`、`onCellEditEnd()` 不触发、结算不跑，和鸿蒙改之前的症状完全同源。
> **安卓要改的就是这一个方法**：把「同列不可编辑就 return」改成「按 `columnIds` 顺序找下一行第一个 `isEditableColumn && isCellEnabled` 的列，找到就 `table.beginEdit(nextRow, 该列)`；全行没有才 `table.endEdit()` + 收键盘」。顺序规则 `isOrderBlocked(nextRow)` 保持在跨行前拦截。

### 2.3 删行后光标必须跟着上移

- 鸿蒙症状：死行删掉、下面的行整体往上顶，但 `moveEditor()` 还拿**删行前的旧下标**，光标落到目标行的下一行（差一格）。
- 鸿蒙最终改法（**复用 `openEditor()` 里已有的机制，不另造平移函数**）：
  ```ts
  const targetRef: FeedData = this.rows[row];   // 结算前记住目标行对象
  this.settleRowsAndPad([]);
  const targetIdx: number = this.rows.indexOf(targetRef);  // 结算后找回新下标
  if (targetIdx < 0) { return; }               // 目标行自己被回收
  this.moveEditor(targetIdx, 目标列);
  ```
  两处：`nextRowDown():1355-1361`、`nextCell():1408-1415`。
- 用户明确裁决：**行号平移本来就是正常的，不要另搞平移逻辑**。曾试过的 `shiftRowAfterRecycle()` 纯函数、`settleAndMoveTo()`、`keepEditor` 参数、配套断言已全部撤销，`RowSettlement.ets` 与 `row-settlement.test.mjs` 回到原样。

> 安卓**不要照搬 `targetRef/indexOf`**：安卓已有 `MixCalcTableView.onRowsRecycled(removedIndices)`（`:139-158`）→ `CellEditorOverlay.shiftRowsAfterRemoval()`（`:173`），并且会同步平移「下一行」按钮的 `nextRowBtn_row`；`MixCalcActivity.finishRowRemoval()`（`:712-725`）在 `setRows()` 之前调用它。安卓改完 2.2 后，只要结算照常触发，光标平移由这套现成机制完成。

### 2.4 两端机制对照（防止改错）

| 环节 | 鸿蒙 | 安卓 |
|---|---|---|
| 完整结算 | `settleRowsAndPad([])` → `settleRows()`（模型层） | `settleZeroRows(emptied)`（Activity 层，内含回收） |
| 换格触发结算 | 换格函数里**显式调用** | `CellEditorOverlay.begin()` 换格 → `notifyEditEnd()` → `onCellEditEnd()` → `table.post(settleZeroRows(emptied))` |
| 光标行号平移 | `targetRef` + `indexOf`（本轮补到两条换格路径） | `onRowsRecycled` / `shiftRowsAfterRemoval`（本来就有） |
| 编辑态失焦 | `TextInput.onBlur` + `windowEvent` + 根布局 `onTouch` 双判据 | `CellEditorOverlay` 没有焦点监听，`end()` 只由用户主动触摸（`handleTap`）触发 —— 系统截屏不会结算 |

真机验证：两轮出包都推 `192.168.1.7:42085`，`install -r -d` → `aa force-stop` + `aa start`，`bm dump` 核对 `0.3.6 / 1000306`；最后一轮包 `dist/mixcalc-0.3.6-debug-signed.hap` 2,707,209 B，SHA256 `474755C1EE75D5F6372B5E500C9B732D223B9FE6461E5AE4AFDBDEC418D27747`。

## 4. 棚号列显示与排版规则（含「9 字符方案被弃用」的完整来龙去脉）

这一章是用户明确要求「计算规则都要记下来」的部分，以后改安卓 `ShedDisplay.java` / `MixCalcTableView.java` / `MixCalcActivity.java` 直接照抄。

### 4.1 为什么弃用「一行 9 字符 + 加宽列」的方案

- 最初照搬安卓：棚号固定 **9 字符/行**、最多两行。为了塞下 9 字符，列宽一路从 **60vp → 68vp → 72vp**，字号也试过 16vp / 15vp / 14vp、13vp。
- **72vp 的代价**：固定列宽合计从 600 涨到 **612dp/vp**，棚号列比其它列宽出一截，**整个表格比例不协调**；而且 `fillsAllColumns` 出现 `600 ≤ 窗口宽 < 612` 的判据缝隙（后来靠平板分支 `isTabletWidth` 提前 return 解决）。用户最终弃用这条「把列撑宽来迁就 9 字符」的路。
- 改走**按显示模式分档**：全列铺满时用 15vp/9 字符，需要横向滚动的手机布局用 14vp/7 字符；列宽退回 **64vp**，只比基线宽 4vp。
- 64vp 的直接原因：14vp 档下 `…21-30…` 这类**双省略号行**在真机 HarmonyOS Sans 字形下约 66.8vp，60vp 列（扣 1vp 边框后可用 59vp）被 `Clip` 裁到只剩 `…`。加宽到 64vp（可用 63vp）解决裁字。这是真机截图 + `[ShedRaw]` hilog 诊断确认的，不是估算。
- 历史教训：项目 `scripts/preview-shed-layout.mjs` 的字形估算（digit 7.0 / dash 3.33 / space 3.5 / ellipsis 11.33）比真实字体度量（7.98 / 6.83 / 3.78 / **14.0**）明显偏小，所以出现过「测算合格、真机裁字」。**以后改显示必须真机截图验收，不能只跑预览脚本。**

### 4.2 最终列宽与硬约束（用户定档，勿改）

```ts
// entry/src/main/ets/common/LayoutRules.ets:15
export const LAYOUT_WIDTHS = [40, 64, 40, 40, 60, 60, 60, 60, 60, 60, 60];
//                                  ↑ 棚号列
export const TABLET_MIN_WIDTH = 600;   // :18
```

- 棚号列 **64vp**；**其余 10 列只能是 40vp 或 60vp**（当前 3 列 40 + 7 列 60），不许出现别的数值。
- 固定列宽合计 **604vp**。窗口 ≥600vp 即全部显示所有列，由 `isTabletWidth` 提前判定，**与 604 无关**（`fillsAllColumns` 里 `isTabletWidth(w) → true`）。
- 单元格左右边框合计 **1vp**，Text 无 padding → 实际可用宽 = `列宽 − 1vp`，64vp 列可用 **63vp**。
- 回归守护：`scripts/model-tests/layout-rules.test.mjs` 有「其余列只能是 40 或 60」的断言。

### 4.3 字号与字符预算分档（必须同源）

| 模式 | 判据 | 棚号字号 | 每行字符预算 |
|---|---|---|---|
| 全列铺满（≥600vp，11 列缩放铺满、无需横向滚动） | `shedAllColumnsVisible() === true` | **15vp** | **9 字符** |
| 需要横向滚动（手机固定列宽） | `false` | **14vp** | **7 字符** |

- 判据唯一来源：`MixCalcTable.shedAllColumnsVisible():665-667` → `isTabletMode()` → `isTabletWidth(viewW)`（≥600vp）。
- 消费点：`fsShed():671-673` 与 `cellText()` 里的 `renderForMode(raw, allColumnsVisible)`（`ShedDisplay.ets:71-73`）。**字号与字符预算必须取同一个判据**，否则会出现「按 9 字符排版却用 14vp 画」或反之。
- 整列统一、**不按行浮动**。正文 16vp、表头 14vp 不受影响。
- 安卓现状：只有一个 `SHED_TEXT_SIZE_DP = 16`，没有模式分档；`TabletLayout` 已有 `isTabletWidth(600)` 判据可以复用。

### 4.4 字符预算的计算公式（`ShedDisplay.ets:23-49`）

```
SHED_CHAR_VP_AT_15 = 8.25    // 15vp 粗体半角字符实测平均占宽
                              // 来源：1008px 真机截图量得 '7-15' 四字符 = 94px
                              //       按 2.85px/vp 换算 = 33vp → 8.25vp/字符
SHED_BORDER_VP     = 1
shedAvailableWidth(w) = max(1, w - 1)
perChar(fs)           = 8.25 * fs / 15
shedMaxCharsAt(w, fs) = clamp(floor(shedAvailableWidth(w) / perChar(fs)), 1, 9)   // 只往下调
renderWithBudget 里 MAX = max(3, floor(charBudget))   // 下限 3 防极窄列算出负的省略号预留位
```

这些「按列宽算预算」的入口（`shedMaxCharsAt` / `shedFontSizeVp` / `renderForColumn` / `render`）现在**只给离线测算和测试用**，应用 UI 走 `renderForMode`。但公式要留着，将来换列宽/换字号时得靠它评估。

字符口径：**数字、短横杠、半角空格、省略号 `…` 各算 1 个字符**；`…` 可紧贴数字，兼作分隔与折叠提示。

### 4.5 两行排版算法（四条铁律 + 分支顺序）

文件头四条铁律（`ShedDisplay.ets:7-11`）：

1. **Range 绝对完整**：绝不把连续区间（如 `3-15`）从中间切断；
2. **每行 ≤ 字符预算、最多 2 行**，任何情况不得爆行；
3. **省略号只在真截断时出现**，无信息丢失时绝不出现；
4. **信息密度优先**：必须截断时优先让首、尾两个关键 Range 都露出。

执行分支（命中即返回）：`A-1 单行全显示 → A-2 两行全显示 → B-1 散点截断 → B-2 双 Range 紧凑折叠`。

**11-12 按 12 组验收清单定档的三处裁决（安卓 `ShedDisplay.java` 还是旧行为）：**

| 分支 | 最终规则 | 旧行为（安卓现状） | 为什么 |
|---|---|---|---|
| **A-2** | 遍历**所有**可行切分 k，取 `|disp(head) − total/2|` 最小的；`diff < bestDiff` 严格小于 → **平手保留更靠前的 k（首行更短）** | 第一个可行 k 就返回 | 旧法产出 `1-3` / `5 7-15`；但单纯「取首行最长」又会把 `1-3 5` / `7 9 11` 挤成 `1-3 5 7` / `9 11` |
| **B-1** | 省略号**紧贴数字不留空格**（`…13 15`），预算 `MAX-1`（原 `MAX-2`） | `… 13 15`，预算 `MAX-2` | 省下的一个字符多露一个号 |
| **B-2** | 首行在首个区间之后**继续贪心补中间词**（`candidate.length <= MAX`，不越过尾部区间）；若中间词**全部**露出，第二行**不加前导省略号**（`1-3 5` / `7-15…`），否则保留（`…21-30…`） | 首行只放 `head='1-3'`，第二行恒带前导省略号 | 满足「首行要 `1-3 5`」这一组诉求 |

另有一条安卓也需要注意的老规则：**只有一个区间时只露一次**（0.3.17 修复，避免 `9-15` 在两行各出现一次像号码重复）。

`preprocess()` 口径（`ShedDisplay.ets:255-333`）：统一连接符 `到/至/~/～/—/－` → `-`、吃掉横杠两边空格，按 `,，、;；/` 或空白切分；解析不出号码时**原文单行兜底**；只取 `a>0`；排序；相邻/重叠区间合并条件 `iv[0] <= last[1]+1`；输出 `a-b` 或单号。`parseJavaInt()` 补齐 Java `NumberFormatException` 语义。编辑态不走这里——点进格子时浮层加载的是**完整原始字符串**。

## 5. 计算规则总表（以后改安卓时逐条对照）

### 5.1 棚号解析与打点覆盖（`ShedCoverage.ets`，安卓 `ShedCoverage.java` 已有同款）

1. 每行棚号展开成具体号码，**同行重复只算一次**；支持 `1-40 / 1到40 / 1至40 / 1~40 / 反向 40-1 / ,，、;；/ 空格 / 1 - 40`。
2. 所有行按顺序铺到同一张「地皮」，**后行优先**（`owner.set(shed, i)` 后面的覆盖前面的）。
3. 每行最终棚数 = 铺完后仍归本行的号码个数（`ownedCounts()`）。
4. `renormalize()` 只重写「被占走部分号码」的行；`mine` 为空时**原样保留**，交给行回收，绝不清空。
5. `shedNumber` 是**声明原文，永不改写**；`shedDisplay` 是派生显示，**不落盘**。

### 5.2 逐行计算（`FeedData.ets`，逐行移植安卓 `FeedData.java`）

```
nonFermentedSum = powder + feed03 + feed05 + feed10
average  = shedCount > 0 ? (nonFermentedSum (+ fermented，按开关)) / shedCount : 0
water    = (nonFermentedSum (+ fermented，按开关)) * waterPercentage / 100
weighed  = shedCount > 0 ? (nonFermentedSum + water + fermented) / shedCount : 0
```

- 批次默认值：`waterPercentage = 20`，`fermentedInWater / fermentedInAverage = false`（`Batch.ets`）。
- `canEditAverage()`：`shedCount > 0` 且非发酵料种数 `< 3` 且（`nf > 0 || fermented > 0`）。
- 手动平均 `applyManualAverage()`：`amount = average * shedCount`；1 种料按 `switchRatio` clamp `0.1~0.9` 拆两格，2 种按比例拆；`mergeSmallerWhenCleared()` 处理清零。
- `updateAllCalculations()`：`countNonFermentedFeeds() !== 2` 时清 `switchRatio`；**绝不在这里重算棚数**，否则手动填料会被误改。
- **顺序铁律**（`MixCalcTable.applyEdit():1117-1121`）：先 `recomputeFirstRow()`（打点覆盖）再 `row.updateAllCalculations(...)`；反了会把棚数临时改回「本行自己数的个数」，导致手动填的料被按 `平均 × 棚数` 重算。
- **覆盖写显示的顺序铁律**（`applyShedCoverage():1042`）：`oldCount` 必须在 `setShedDisplay` **之前**取，否则棚数变化时「平均 × 新棚数」会拿错基数。
- 所有行平等：**没有「第一行 = 总棚数」**，`isWarningCell()` 恒 false；棚数列只读。

### 5.3 表尾 / 合计 / 误差（`MixCalcTable.ets:2189-2252`、`Index.computeError():339-368`）

- `sumColumn(2)` = Σ 棚数；料/水列合计**跳过 `shedCount <= 0` 的行**（防重叠棚算两遍）。
- `filledRows()` = `shedCount > 0` 的行数 → 表尾列 0 显示 `有棚行数/总行数`。
- 表尾列 3 = 加权平均 `Σ(average × shedCount) / Σ shedCount`，四舍五入 2 位；料/水列没数据显示 `0` 不留空。
- 误差：`Σ(fermented+powder+feed03+feed05+feed10+water) − Σ(round(weighed,2) × shedCount)`，同样跳过 0 棚行；`|err| < 0.005` 或无数据显示空，否则带符号 `toFixed(2)` 且截到 5 字符。

### 5.4 行回收结算（`RowSettlement.ets`，安卓 `RowSettlement.java` 同款）

```
settleRows(rows, emptiedByUser):
  total = rows.length
  removed = recycleDeadRows(rows, emptiedByUser)      // ① 先回收
  cleared = settleZeroRowData(rows)                   // ② 再兜底清
  while (rows.length < total) rows.push(new FeedData()) // ③ 底部补空行，行数守恒
  return { removed, changed }
```

- `recycleDeadRows()`：有效棚数**一律按声明文本重算**（`ownedCounts(texts)`），**绝不读 `row.shedCount` 缓存**（缓存可能滞后，会导致「一行一行往上进」）。`owned[i] > 0` 保留；死行判据 = `(shedNumber.trim() !== '' || hasRowData(row)) || emptiedByUser` **包含 i**；纯空行不删；记录升序下标后**从后往前 splice**。
- `hasRowData()`：平均/发酵料/粉料/0.3/0.5/1.0/水/称料/换料比例任一非 0，或 `isAverageManuallyModified`。
- `settleZeroRowData()`：`shedCount > 0` 或无数据跳过；否则把上述 9 个字段清 0 + 复位手动平均标记，**棚号列不清**。
- **顺序不能反**：回收会连棚号一起拿掉，兜底清只动留下的行。
- 结算时机（只在「用户真正离开编辑」）：换格、失焦定稿、切批次、退后台、载入、删棚号删空、转入转出。**编辑途中绝不删行**（显示层只把 0 棚行的料列置灰，数据留着，棚数回来能立刻恢复）。
